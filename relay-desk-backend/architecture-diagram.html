Relay Desk — Admin / Dealer Authorization Architecture

How roles, branches, and client codes control what each user can see.

1. Application authorization flow

What happens from login to data being shown, for each role.

Login
email + password
↓
JWT issued
{ id, role, branch_id }
↓
Request hits API
Authorization: Bearer <token>
↓
Role middleware checks token
↓
role = admin
No filter applied
SELECT * FROM clients
↓
Sees ALL branches
Delhi, Mumbai, Pune, ...
Admin can view, edit, and reassign any client, ticket, or dealer across every branch.
role = dealer
Filter by branch_id
SELECT * FROM clients
WHERE branch_id = token.branch_id
↓
Sees ONLY their branch
e.g. Delhi clients only
Dealer's own row in agents stores their branch_id — every query is automatically scoped to it, so a Delhi dealer can never see Mumbai's clients even by guessing a client code.
Where this lives in code: a small middleware (e.g. scopeToBranch.js) reads req.agent.role and req.agent.branch_id from the JWT (set at login) and either leaves the SQL query untouched (admin) or appends WHERE branch_id = ? (dealer) before it reaches the controller. Controllers themselves don't need to know about roles — the middleware does the filtering for them.

Key relationship: agents.branch_id and clients.branch_id both point to the same branches table — that shared branch is what lets a dealer's queries be scoped to "only clients in my branch," and lets an admin query across all branches at once.
